# 2A.0 — Semânticas de `model_id_fallback` (antes de mapear para Advisor)

Estado: **documento de análise**; nenhuma linha de roteamento foi alterada. Caminhos relativos a `applications/` (branch `evo/p2a-a`, a partir de `dev` com a Fase 1). Fonte do plano: `evolution/07-plano-de-execucao.md` (2A.0, D1b, D3); baseline: doc 16.

**Resumo.** `model_id_fallback` (coluna `tenant_llm_configs.model_id_fallback`, migration 024; espelho em `zentriz_llm_config`, 126) carrega hoje **cinco** comportamentos diferentes. Só os usos 1 e 2 são "subir de capacidade" (Advisor). O uso 3 é consequência do 1. O uso 4 é **disponibilidade** e não pode virar Advisor. O uso 5 é config de plataforma que a LEI dos slots manda remover.

## Pontos que não são usos do fallback mas confundem
- `cyborg_model_id` e `cyborg_model_id_fallback` (migration 029): o V3 **não os lê** (usa `_SLOT_LLM` e o fallback do slot); só o V2 (`cyborg_v2.py:165-190`). Mapeados em D3: valor migra para Advisor **somente** se o Advisor estiver vazio.
- Rótulo de UI "Fallback (rework / QA)": `genesis-web/components/llm/LlmSlotEditor.tsx` (fora do escopo de 2A.0 a 2A.3; muda em 2A.10).
- `fallback == principal` (ex.: `opus-4-8` e `opus-4-7`, migration 030): para o backfill (2A.3) é registrado como Advisor **NULL** ("sem escalada"), não como cópia do principal, para o Advisor vazio ter sentido único (D1b).

## Consequência para 2A.3 (o que o backfill pode mapear)
Somente as semânticas **1 e 2** vão para `model_advisor`. A 3 é derivada. A 4 e a 5 não mapeiam para nenhum papel. Como a coluna antiga não distingue as semânticas, o backfill mapeia o valor para Advisor (é o uso real de rework) e **o código de 2A.4+ é que impede** que a 4 use o Advisor. Enquanto houver agents antigos, as colunas antigas continuam autoritativas (dupla escrita).
