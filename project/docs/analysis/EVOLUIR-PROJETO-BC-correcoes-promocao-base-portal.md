## 2. Causa do 404 do `disk-copy` (D-4) — o que está e o que não está provado

- **Provado no código:** `isPermanentGitError` (`evolveClaim.ts`, regex `requested url returned error: 40[134]`) trata 401/403/404 como **permanentes**, e o ramo permanente caía em `disk-copy` sem alarme; `evolutionSourceError` ficava só no retorno de `/promote`. A cópia vinha de `filesRoot/<head>/apps`, ou seja, do disco do v7 aceito e não mergeado.
- **Não provado:** por que o GitHub devolveu 404 na 3ª promoção (e não nas duas primeiras). Só o corpo do `/promote` foi guardado; não há log do `git fetch`/token. Hipóteses coerentes com o código, a verificar na próxima rodada com os logs da API: (a) GitHub responde 404 (não 403) a token de instalação sem acesso ou ainda não propagado, e o token é cunhado escopado ao repositório (`repositoryNames`, `contents:write`) a cada passo; (b) indisponibilidade transitória logo após o push de `evolution/v7`. Nenhuma delas muda a decisão: com repositório conhecido, **falhar e repetir** é seguro; copiar do disco não é.
- A parte "GET `refs/heads/evolution/v7` 404" do relatório vem do cliente de API do GitHub (não do `stepCode`) e não foi investigada além disso.

## 4. Riscos e pendências

1. **Prova de merge consulta o GitHub na promoção** (uma chamada por promoção quando o HEAD é filho de card com repositório). GitHub indisponível ⇒ `pr_lookup_failed` ⇒ promoção recusada (fail-closed). Aceito: é o mesmo contrato da entrega.
2. **"Explicitamente superado" = rejeitar o card anterior** (e descartar o filho); não criei atalho/flag para ignorar o PR (seria reabrir o D-4). Decisão do Jean se quiser um `supersedePrevious` auditado.
3. **Verificação fora do lock:** a regra roda antes do claim; uma promoção que ganhe a corrida não é afetada (o claim mantém `EVOLUTION_IN_FLIGHT`/`BASE_STALE`). Não há janela em que duas promoções criem filhos: o índice/lock da linhagem continua sendo a trava.
4. **`factoryHealth` só existe para filhos aceitos depois deste deploy** (os gates são gravados no aceite); filhos antigos mostram `null`. Os gates refletem o aceite; se o QA/FULL-TEST mudar depois (republicação), `recordScopeGate` regrava.
5. **Tenant com cards em andamento:** um card promovido sobre filho aceito não mergeado agora fica `ready` com 409; é o comportamento desejado, mas o operador precisa mergear/rejeitar o PR anterior (RUNBOOK §2.7). TK-0007/v8 do ambiente dev (PR #9 com o código do #8) continua exigindo refazer sobre `dev` limpo.
6. **Config nova:** `EVOLVE_CARD_DISK_COPY` (variável de ambiente, default desligado). Não é flag de tenant.
7. D-1/D-2/D-3/D-8 seguem abertos na frente `evo/u1`; sem eles o `factoryHealth` mostra a verdade (FULL-TEST reprovada ⇒ `failed`), mas o aceite do Cyborg continua vazio.
