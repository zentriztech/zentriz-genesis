## 3. Respostas às perguntas do ataque

1. **Claim em corrida e queda.** É seguro para o que foi pensado: advisory lock por linhagem com raiz estável (`resolveLineageRoot` fora do lock, mas imutável), idempotência relida sob o lock, ticket `FOR UPDATE` e CAS na mesma transação do `INSERT` (sim, **mesma transação**). A versão sai do HEAD correto (`resolveLineageHead` exclui o pai com filho `accepted`), e o número de uma tentativa `failed`/`archived` é reaproveitado (teste verde). O `reset --hard` só roda quando o `takeOrRenewLease` confirma `status='materializing'` no início do passo. Janelas **não cobertas**: passo maior que o lease (M-04), `failTerminal` sem CAS de dono (M-04), erro transitório gravado como concluído (M-05), ticket recusado durante a materialização (M-11), `DELETE` de ticket em corrida (M-07), crash entre `finalize` e recompute (M-21).
2. **Índices no boot.** O DDL confere com H §3.1. Sem `CONCURRENTLY`, o lock é `SHARE` (bloqueia escrita, não leitura) e dura pouco **se** obtido; falta teto de espera (M-09). Uma falha de pré-checagem não derruba a API (catch por índice, teste "boot sujo" verde). Com a flag `off` e os índices presentes, o comportamento **não** é byte-idêntico: a corrida vira 409 e há um 409 determinístico novo no `/api/specs` (M-02). Isso viola a promessa "byte-idêntico com a flag `off`", embora H §2 aceite a primeira parte.
3. **Migrations 141–145.** Numeração contínua, ordem correta, nenhuma colisão de versão (a chave é o nome do arquivo). Rodei duas vezes: a segunda deu "All migrations up to date". O conteúdo é idempotente (`IF NOT EXISTS`, `WHERE NOT EXISTS`, `DROP CONSTRAINT IF EXISTS`). Nenhum código ou teste referencia o nome antigo; só restam comentários velhos (M-18).
4. **Flags.** Por tenant (com env vencendo): `EVOLVE_CLAIM`, `TICKET_TRANSITIONS`, `EVOLUTION_PROMOTE_BANCADA`. Globais: `ATTACHMENTS_STRICT` (api **e** runner, sem coordenação), `TASK_INHERIT_TRANSITIVE` (runner), `EVOLVE_RECONCILER`. Caminhos que ignoram flag: índices de unicidade (sempre), rotas novas (M-19), `recomputeProductLifecycle` no legado só com 1.7. O risco está detalhado em M-03.
5. **`ticketTransitions`.** A tabela é coerente com `reopenTicketsOfChild` estrito (reabre só `promoted`) e com o PATCH; a repetição é idempotente (200 sem evento); a auditoria grava UUID e código, sem PII. Buracos: o legado e o reconciliador escrevem sem CAS ou sem evento (M-07), e `promoted→rejected` acontece com filho em materialização (M-11).
6. **Herança transitiva.** `TSK-INH-V<n>-…` é compatível com o regex, com os `LIKE` da API e com as exclusões de Dev/QA (M-24 tem só o rótulo de fallback). `TSK-FULL-TEST` e `TSK-DEVOPS-001` nunca viram herdadas.
